# Data Model: Simple Todo REST API

## Task

Represents one user task.

| Field | Type | Rules |
|-------|------|-------|
| `id` | `Long` | System-generated by the in-memory repository; unique for the lifetime of the running application. Clients cannot choose it. |
| `title` | `String` | Required; a value for which `String.isBlank()` is true is rejected by the service. Other nonblank input is retained as submitted. |
| `status` | `TaskStatus` | Required; only `TODO` or `DONE`. A new task starts as `TODO`. |

### Lifecycle

- Application startup seeds at least three tasks with unique system-generated Long ids and nonblank titles.
- Creating a task validates its title in the service, assigns an id, sets `TODO`, and stores it in the in-memory repository.
- Completing a `TODO` task changes its status to `DONE`.
- Completing a `DONE` task again succeeds without changing it.
- An unknown id produces the API outcome `NOT_FOUND`; this is not a task status and does not change stored tasks.
- All in-memory tasks are lost when the application stops.
- Task ordering is not guaranteed; concurrent request behavior is outside this feature's scope.

## TaskStatus

An enum with exactly these values:

- `TODO`: the task is not complete.
- `DONE`: the task is complete.

No reverse transition from `DONE` to `TODO` is part of this feature.

## API Error

An error response contains:

| Field | Type | Rules |
|-------|------|-------|
| `code` | `String` | Machine-readable code: `BAD_REQUEST`, `VALIDATION_ERROR`, or `NOT_FOUND`. |
| `message` | `String` | User-facing explanation in Persian. |

Errors are response data, not persisted entities. No user, account, or relationship entity is required.
